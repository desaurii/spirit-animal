# Предложения по улучшению

Это список для обсуждения, а не план внедрения. У предложений разная польза и масштаб: некоторые относятся к конкретным особенностям текущего кода, другие — необязательные идеи, затраты на которые могут превысить пользу для небольшого приложения. Ни одно предложение не считается одобренным.

## 1. Проверять на сервере точный набор ответов

**Файл:** `src/app/api/spirit-animal/route.ts`

1. **Как работает сейчас:** Маршрут проверяет, что для каждого вопроса из списка передан допустимый ответ. Но он не отклоняет дополнительные ключи, а требование ровно одного ответа на вопрос подразумевается проверкой через `questions.every`. Запрос со всеми правильными ответами и посторонними данными всё равно принимается и передаётся модели.
2. **Что предлагается:** Требовать, чтобы ключи запроса в точности совпадали с ID вопросов, и продолжить проверять допустимость каждого ответа. При пропущенном или лишнем ответе возвращать `400`.
3. **Какую проблему решает:** Делает контракт API однозначным и не позволяет посторонним данным попасть в промпт. Это также защитит маршрут, если к нему будут обращаться не только из этого интерфейса.
4. **Компромиссы:** Проверка станет немного сложнее и потребует изменений, если позже появится возможность отправлять неполные ответы. Слишком жёсткое сравнение усложнит добавление необязательных вопросов.
5. **Почему это уместно здесь:** В опросе есть фиксированные 15 вопросов и сценарий «один ответ на каждый», поэтому такой контракт легко описать и проверить.

## 2. Ограничить размер входящего запроса

**Файл:** `src/app/api/spirit-animal/route.ts`

1. **Как работает сейчас:** Маршрут разбирает JSON и проверяет его форму, но `answers` — это запись с произвольными строковыми ключами и значениями. Явного ограничения размера тела запроса до разбора нет.
2. **Что предлагается:** Установить разумный предел размера запроса и ограничить количество и длину ключей и значений ответов, помимо проверки ID вопросов и допустимых вариантов.
3. **Какую проблему решает:** Снижает вероятность того, что слишком большой или некорректный запрос напрасно израсходует память или будет передан модели.
4. **Компромиссы:** Пределы нужно выбрать и задокументировать. Если вопросы или варианты ответов станут длиннее, ограничения придётся пересмотреть. Часть таких ограничений уже может обеспечиваться платформой размещения.
5. **Почему это уместно здесь:** Допустимые ответы короткие и заданы заранее, поэтому небольшой лимит не должен мешать обычному прохождению опроса.

## 3. Ограничить частоту запросов к платному API

**Файлы:** `src/app/api/spirit-animal/route.ts`, возможно, конфигурация размещения

1. **Как работает сейчас:** Любой, кто может обратиться к маршруту и отправить правильные ответы, может запросить результат модели. Ограничения частоты по пользователю, IP-адресу или всему приложению нет.
2. **Что предлагается:** Добавить умеренное ограничение частоты. Если приложение работает на нескольких экземплярах сервера, возможно, потребуется общее хранилище для счётчиков. Предел нужно выбрать с учётом предполагаемой нагрузки и хостинга.
3. **Какую проблему решает:** Ограничивает автоматические всплески запросов, которые могут увеличить расходы на API или сделать маршрут недоступным для обычных пользователей.
4. **Компромиссы:** Надёжный распределённый ограничитель добавляет внешнюю зависимость, настройку и риск ложных срабатываний для пользователей с общим IP-адресом. Ограничитель только в памяти проще, но может работать непоследовательно на бессерверном хостинге или после перезапуска.
5. **Почему это уместно здесь:** Каждый принятый запрос может стоить денег. Это реальный эксплуатационный вопрос для публичного маршрута, хотя для личной демонстрации дополнительная инфраструктура может оказаться избыточной.

## 4. Защититься от повторной отправки

**Файлы:** `src/components/quiz/Quiz.tsx`, при необходимости `src/app/api/spirit-animal/route.ts`

1. **Как работает сейчас:** Кнопка Next блокируется после того, как React обновит `isLoading`. Два очень быстрых нажатия могут произойти до этого обновления; повторная отправка возможна также из-за сетевого повтора или дублирующего запроса.
2. **Что предлагается:** Добавить немедленную защиту от повторного вызова на клиенте, например через `ref`. Если важно не допускать повторной оплаты при сетевых повторах, рассмотреть механизм идемпотентности на сервере.
3. **Какую проблему решает:** Не позволяет начать несколько запросов к модели для одной активной отправки.
4. **Компромиссы:** Клиентская защита небольшая, но не защищает от прямых запросов к API или повтора после потери ответа. Серверная идемпотентность потребует идентификаторов запросов и хранилища результатов, что заметно усложнит решение.
5. **Почему это уместно здесь:** Последний шаг запускает платный сетевой запрос, поэтому повторные вызовы важнее, чем при локальном изменении состояния.

## 5. Обрабатывать ошибки браузерного хранилища без падения приложения

**Файл:** `src/lib/storage.ts`

1. **Как работает сейчас:** Разбор JSON и проверка схемы в `getQuizState` защищены от ошибок, но чтение, запись и удаление из `localStorage` находятся вне этих обработчиков. Браузер может выбросить исключение, если доступ к хранилищу запрещён или оно недоступно.
2. **Что предлагается:** Явно обрабатывать ошибки доступа к хранилищу и позволять опросу работать на состоянии в памяти, если сохранение недоступно. При желании можно удалять некорректные сохранённые данные после их обнаружения.
3. **Какую проблему решает:** Настройки приватности браузера или сбой хранилища не должны ломать запуск опроса или изменение ответа.
4. **Компромиссы:** Ошибки станут менее заметны, если их не регистрировать или не показывать пользователю. Также нужно решить, сообщать ли, что прогресс не будет сохранён.
5. **Почему это уместно здесь:** Локальное хранилище нужно для удобства, а не для основной работы приложения, поэтому его недоступность обычно не должна мешать отвечать на вопросы.

## 6. Решить, нужно ли восстанавливать результат после обновления страницы

**Файлы:** `src/lib/storage.ts`, `src/components/quiz/Quiz.tsx`

1. **Как работает сейчас:** Текущий шаг и ответы сохраняются, но `result` хранится только в состоянии React. Если обновить страницу после появления результата, пользователь вернётся к опросу, хотя ответы останутся сохранёнными.
2. **Что предлагается:** Если восстановление результата желательно, сохранять проверенный результат вместе с состоянием опроса и восстанавливать его при загрузке. Сохранить проверку схемы и версии, а при повторном прохождении очищать результат.
3. **Какую проблему решает:** Пользователь не потеряет результат после обновления страницы или возвращения на неё.
4. **Компромиссы:** Результат — персональные данные в браузерном хранилище; он может устареть при изменении схемы или промпта. Понадобятся версия и миграции. Альтернатива — повторно вычислять результат, но это приведёт к ещё одному запросу к модели.
5. **Почему это уместно здесь:** Приложение уже сохраняет ответы для восстановления прогресса, поэтому сохранение результата — естественное, но необязательное продолжение этого подхода.

## 7. Ужесточить проверку текста, сгенерированного моделью

**Файл:** `src/types/quiz.ts`

1. **Как работает сейчас:** Схема результата проверяет строковые типы и количество сильных сторон от трёх до пяти, но текстовые поля могут быть пустыми или сколь угодно длинными, а сами сильные стороны могут содержать пустые строки.
2. **Что предлагается:** Рассмотреть обрезку пробелов и разумные минимальные и максимальные длины для названия животного, слогана, объяснения, сильных сторон и предостережения.
3. **Какую проблему решает:** Не позволяет неожиданному или чрезмерно длинному тексту создавать пустые разделы, нарушать вид карточки или неоправданно увеличивать ответ.
4. **Компромиссы:** Жёсткие пределы могут отклонять полезный текст модели и приводить к повторному запросу или ошибке. Границы должны соответствовать желаемому стилю и могут потребовать корректировки после просмотра реальных результатов.
5. **Почему это уместно здесь:** Результат отображается в компактной карточке, а в проекте уже используется Zod для проверки структурированного ответа.

## 8. Явно обрабатывать отсутствие API-ключа

**Файлы:** `src/lib/openai.ts`, `src/app/api/spirit-animal/route.ts`

1. **Как работает сейчас:** Клиент OpenAI создаётся при загрузке модуля из `process.env.OPENAI_API_KEY`. В README сказано, что ключ необходимо настроить, но маршрут не проверяет наличие настройки и не отличает отсутствие ключа от ошибки модели.
2. **Что предлагается:** Создавать или получать клиент только при необходимости и явно обрабатывать отсутствие ключа в серверной конфигурации. Секрет не должен попадать в ответы клиенту или логи.
3. **Какую проблему решает:** Упрощает диагностику локальной настройки и ошибок развёртывания, а также снижает риск того, что сам импорт маршрута неожиданно завершится ошибкой.
4. **Компромиссы:** Появится немного дополнительной логики; нужно решить, какие детали показывать в серверных логах, а какие — пользователю. Настроить секрет всё равно будет необходимо.
5. **Почему это уместно здесь:** API-ключ — единственный обязательный секрет приложения, указанный в документации, поэтому понятная ошибка особенно полезна при настройке.

## 9. Сделать выбор модели настраиваемым

**Файлы:** `src/lib/openai.ts`, `README.md` с инструкцией по настройке

1. **Как работает сейчас:** Идентификатор модели записан строкой непосредственно в серверном помощнике. Чтобы его изменить, нужно редактировать код.
2. **Что предлагается:** Читать идентификатор модели из серверной переменной окружения, при необходимости задав осознанное значение по умолчанию, и описать настройку в документации.
3. **Какую проблему решает:** Позволяет менять модель настройкой развёртывания, не редактируя код, и облегчает поиск используемой модели.
4. **Компромиссы:** Дополнительная настройка может привести к различиям между средами или сбою из-за опечатки. Значение по умолчанию может скрыть отсутствие явного выбора, а обязательная переменная усложнит настройку.
5. **Почему это уместно здесь:** Вызов модели уже изолирован в одном помощнике, а API-ключ тоже передаётся через переменную окружения. Это небольшое расширение, если предполагается менять модель.

## 10. Настроить тайм-аут и обработку сбоев запроса к модели

**Файл:** `src/lib/openai.ts`

1. **Как работает сейчас:** Функция ожидает завершения `openai.responses.parse` без заданного в этом помощнике тайм-аута или политики повторов. Любая ошибка затем обрабатывается как общая ошибка сервера.
2. **Что предлагается:** Выбрать ограниченный тайм-аут и, только для подходящих временных сбоев, ограниченное число повторов. Учитывать лимит времени самого хостинга.
3. **Какую проблему решает:** Снижает вероятность бесконечного ожидания и позволяет восстановиться после некоторых временных ошибок внешней службы.
4. **Компромиссы:** Повторы могут увеличить задержку и расходы; они не всегда безопасны, если первый запрос завершился, но ответ потерялся. Тайм-аут может завершить запрос, который в итоге успешно выполнился бы.
5. **Почему это уместно здесь:** На последнем шаге пользователь ждёт синхронный ответ, зависящий от внешней модели, поэтому ограниченное время ожидания важно для взаимодействия.

## 11. Показывать пользователю более полезные ошибки API

**Файлы:** `src/lib/api.ts`, `src/components/quiz/Quiz.tsx`, `src/components/quiz/QuizError.tsx`

1. **Как работает сейчас:** Клиент проверяет успешные ответы, но при любом сбое `Quiz` показывает один и тот же текст. Сервер различает некорректный ввод (`400`) и ошибку генерации (`500`), но клиент этим различием не пользуется.
2. **Что предлагается:** Определить небольшой формат клиентских ошибок и сопоставлять ожидаемые сбои понятным сообщениям. Внутренние детали и секреты не показывать; для неизвестных ошибок оставить общее сообщение.
3. **Какую проблему решает:** Помогает понять, нужно ли исправить ввод, попробовать позже или проверить соединение.
4. **Компромиссы:** Больше сообщений и типов ошибок означает больше состояний интерфейса. Слишком подробная информация может раскрыть внутреннее устройство или запутать пользователя.
5. **Почему это уместно здесь:** Кнопка повтора уже есть, но текущее сообщение не объясняет, поможет ли повторная попытка.

## 12. Оформить варианты каждого вопроса как семантическую группу переключателей

2. **Что предлагается:** Представить вопрос как `fieldset` с `legend` и задать радио-кнопкам общее имя, производное от ID вопроса. Сохранить управляемое состояние React и текущий внешний вид.
3. **Какую проблему решает:** Делает группу ответов понятнее вспомогательным технологиям и возвращает стандартное поведение радио-группы, например перемещение стрелками и взаимоисключение вариантов.
4. **Компромиссы:** Может понадобиться сбросить стандартные стили `fieldset`, а оформление заголовка перенести на `legend`. Разметку следует проверить с клавиатурой и программами чтения с экрана.
5. **Почему это уместно здесь:** Основное действие приложения — выбор одного ответа из нескольких, что напрямую соответствует стандартной группе радио-кнопок.

## 13. Разрешить переход по опросу с клавиатуры через отправку формы

**Файлы:** `src/components/quiz/QuizContent.tsx`, `src/components/quiz/QuizActions.tsx`, `src/components/quiz/Quiz.tsx`

2. **Что предлагается:** Обернуть текущий шаг в форму и вызывать ту же логику `handleNext` при её отправке. Кнопку Back нужно сделать кнопкой без отправки формы; текущую проверку ответов и блокировку во время загрузки сохранить.
3. **Какую проблему решает:** Позволяет пользоваться основным действием без мыши и добавляет привычную семантику формы.

5. **Почему это уместно здесь:** Опрос — это последовательный ввод ответов с понятным основным действием, поэтому отправка с клавиатуры улучшает доступность и удобство.

4. **Компромиссы:** Слишком широкое применение живых объявлений может создавать шум или повторять сообщения. Роли и приоритет объявления стоит проверить со вспомогательными технологиями.
5. **Почему это уместно здесь:** В приложении уже есть асинхронные состояния загрузки и ошибки; нужно сделать их заметными не только визуально.

## 16. Хранить определение шагов опроса в одном месте

**Файлы:** `src/types/quiz.ts`, `src/lib/storage.ts`, `src/components/quiz/Quiz.tsx`, возможно, `src/components/quiz/Progress.tsx`

1. **Как работает сейчас:** Тип шага задан как `1 | 2 | 3`, схема хранилища отдельно ограничивает шаг числом 3, `Quiz` вычисляет последний шаг по данным вопросов, а `Progress` жёстко задаёт три визуальных шага.
2. **Что предлагается:** Определить, должны ли шаги быть фиксированными или вычисляемыми. Если число шагов должно следовать из данных вопросов, централизовать метаданные или общую логику проверки и отображения. Если число шагов фиксировано намеренно — задокументировать это правило и согласовать с ним код.
3. **Какую проблему решает:** Снижает риск того, что несколько определений разойдутся, когда вопросы будут перераспределены.
4. **Компромиссы:** Построение схемы Zod во время выполнения на основе данных требует аккуратных границ между модулями. Общая константа проще, но её всё равно нужно менять вместе с опросом. Фиксированные значения менее абстрактны и могут быть вполне достаточны.
5. **Почему это уместно здесь:** Одна и та же предпосылка о трёх шагах повторяется в типах, сохранении состояния и интерфейсе, что заметно даже в небольшом проекте.

## 17. Синхронизировать шаг опроса с навигацией браузера

**Файлы:** `src/components/quiz/Quiz.tsx`, `src/app/quiz/page.tsx`

1. **Как работает сейчас:** Текущий шаг хранится в состоянии React и localStorage. Кнопки браузера «Назад» и «Вперёд» не перемещают между шагами; для этого есть только кнопка Back внутри приложения.
2. **Что предлагается:** Рассмотреть синхронизацию шага с параметром URL или аккуратно управляемой историей браузера, не записывая в URL текст ответов.
3. **Какую проблему решает:** Делает навигацию браузера более ожидаемой и может позволить открыть ссылку на определённый шаг.
4. **Компромиссы:** Нужно согласовать URL с сохранёнными ответами, обработать недопустимые номера шагов, перезагрузку и дублирование записей истории. Прямая ссылка на шаг может запутать, если ответов для него ещё нет.
5. **Почему это уместно здесь:** В опросе уже есть переход назад, поэтому навигация браузера может дополнить существующее поведение. Это необязательно, если ожидается, что пользователи будут пользоваться только кнопками на странице.

## 18. Определиться, должен ли интерфейс использовать Geist или Arial

**Файлы:** `src/app/layout.tsx`, `src/app/globals.css`

1. **Как работает сейчас:** Корневой компонент загружает Geist и Geist Mono и добавляет их CSS-переменные в `<html>`, но правило `body` явно задаёт Arial. Поэтому переменные Geist, похоже, не используются для основного текста.
2. **Что предлагается:** Либо применить переменную Geist к `body` или Tailwind-классом, либо убрать загрузку шрифтов и переменные, если Arial выбран намеренно.
3. **Какую проблему решает:** Убирает лишнюю загрузку шрифтов или действительно применяет задуманный шрифт; также устраняет противоречие между двумя вариантами типографики.
4. **Компромиссы:** Изменение шрифта влияет на переносы строк и визуальный стиль. Удаление загрузки внешнего шрифта может повысить надёжность и приватность, но изменит вид; применение Geist может сохранить исходное намерение, но требует визуальной проверки.
5. **Почему это уместно здесь:** Несоответствие явно видно в текущем layout и глобальных стилях, поэтому это конкретная чистка с заметным визуальным эффектом.

## 20. Добавить идентификатор запроса для диагностики ошибок сервера

**Файл:** `src/app/api/spirit-animal/route.ts`

1. **Как работает сейчас:** Маршрут записывает общее сообщение и ошибку в лог, затем возвращает общий ответ `500`. Идентификатора, по которому можно связать обращение пользователя с записью в логе, нет.
2. **Что предлагается:** Назначать безопасный идентификатор запросу, добавлять его в структурированные серверные логи и возвращать вместе с общим сообщением об ошибке.
3. **Какую проблему решает:** Упрощает расследование сбоев в рабочем приложении, не раскрывая пользователю подробности поставщика модели или содержимое ответов.
4. **Компромиссы:** Появятся дополнительные соглашения по логированию и ответам. Идентификатор полезен только при наличии сохраняемых и доступных для поиска логов; ответы и секреты нельзя записывать.
5. **Почему это уместно здесь:** Ошибки модели сейчас скрыты за общим сообщением интерфейса, поэтому идентификатор поможет разбирать обращения пользователей, если приложение будет развёрнуто для реальной аудитории. Для локальной демонстрации пользы может быть мало.
